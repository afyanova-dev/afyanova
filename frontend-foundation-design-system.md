# Design System Foundation (CSS)

**Status:** Phase 2 delivered — shared components migrated to foundation patterns
**Last reviewed:** 2026-10-17
**Owner:** frontend

## 1. Purpose

Afyanova uses Carbon (@carbon/react v1) as its design system. Default Carbon
components alone under-designed many workspace screens, so past fixes accreted
into one 4,320-line `resources/css/app.css` with no layering, token discipline,
or ownership rules.

This foundation fixes the structure so future UI improvement is incremental:

1. **Better UI without deviating from Carbon.** All custom styling consumes
   Carbon design tokens. Zero raw colors, sizes, or spacing in app CSS.
2. **Theme-safe by construction.** white / g10 / g90 / g100 (light and dark)
   are supported because nothing hardcodes light-theme values.
3. **A foundation before per-page redesign.** Workspace screens adopt the
   patterns domain-by-domain (phases below); they do not fork them.

## 2. Structure and import order

`resources/css/app.css` is the only Vite entry. Imports define the cascade:

| Order | File | Responsibility |
|---|---|---|
| 1 | `@carbon/styles/css/styles.css` | Carbon itself — source of truth |
| 2 | `tokens.css` | `--afy-*` semantic tokens, every value a Carbon token |
| 3 | `legacy/<domain>.css` | Workspace styles, split verbatim from the former app.css; cascades before the foundation |
| 4 | `foundation.css` | `.afy-*` page scaffold + design-system patterns |

Naming contract:

- `.afy-*` — design-system patterns (foundation.css, tokens for components).
- Workspace prefixes (`.pharmacy-`, `.front-desk-`, `.patient-chart-`, …) stay
  in their legacy file until that workspace migrates to the foundation.
- `.afyanova-*` — app/chrome classes that predate the foundation (shell,
  skip link, docked panel …); migrate opportunistically, do not add new ones.

## 3. Token system (`tokens.css`)

Every `--afy-*` value is `var(--cds-*, <fallback>)`. The fallbacks mirror
Carbon's light-theme primitive values and exist only because some Carbon
custom properties are context-dependent; without them the same token would
still resolve on any theme class Carbon emits.

The **expression layer** aliases (`--afy-canvas`, `--afy-surface`,
`--afy-surface-interactive`, `--afy-hairline`, `--afy-elevation-rest/hover`)
implement the "soft clinical" look: a gray canvas with raised cards in light
themes, near-black canvas with raised layers in dark themes. Because this
inverts Carbon's white-theme layering direction, those five tokens are
re-mapped per Carbon theme class at the bottom of `tokens.css`
(`.cds--g10/.cds--g90/.cds--g100` — `.cds--white` uses the defaults). Adding
a theme = adding it to those selectors.

| Group | Tokens | Meaning |
|---|---|---|
| Spacing rhythm | `--afy-space-2xs … --afy-space-2xl` | Carbon 2x steps 2–8; the steps foundation patterns use |
| Expression surfaces | `--afy-canvas`, `--afy-surface`, `--afy-surface-interactive` | Workspace backdrop; raised card surface; quiet hover tint (color-mix of the two, theme-balanced) |
| Shell chrome | `--afy-rail` | Sidenav surface, distinct from the canvas in every theme (Carbon ships them identical — documented limitation) |
| Legacy layer surfaces | `--afy-surface-hover/selected/selected-hover`, `--afy-surface-accent`, `--afy-surface-field`, `--afy-surface-inverse`, `--afy-surface-page` | Raw Carbon layer semantics (fields, inverse chips); `--afy-surface-page` now aliases the canvas |
| Borders | `--afy-hairline` (half-tone panel edge), `--afy-border`, `--afy-border-strong`, `--afy-focus` | Hairline is rgba ink/10% by theme; borders stay Carbon; focus ring stays Carbon blue |
| Text | `--afy-text-primary/secondary/helper/placeholder/on-color`, `--afy-link` | Standard text roles |
| Status | `--afy-status-positive/caution/negative/information` | Carbon support colors for chips (tint + deepened ink via color-mix), dots, and deltas |
| Radius | `--afy-radius` (2px), `--afy-radius-lg` (4px, reserved), `--afy-radius-pill` (100px) | Carbon product radius only — surfaces square, chips/pills round |
| Elevation | `--afy-elevation-rest`, `--afy-elevation-hover`, `--afy-elevation-panel` (the strongest, docked drawers; all `none` in g90/g100 where surfaces elevate by lightness), legacy `--afy-shadow-1..3` | Expression primitives for panels |
| Motion | `--afy-duration-fast/moderate/interaction/slow`, `--afy-easing` | Carbon motion primitives (70/110/150/240ms); the 150ms interaction duration matches Carbon's tile transition |
| Stacking | `--afy-z-panel` (7000), `--afy-z-shell` (8000), `--afy-z-header` (8001), `--afy-z-sheet` (9000) | The layer plan already in use; documented for new floating UI |

Hard rules:

- No raw hex, shadow, radius, duration, or spacing values outside tokens.css.
  New token? Add it here first, bridged to Carbon.
- Tokens resolve at `:root` (theme class on `<html>`), so afy- components do
  not re-resolve inside Carbon `<Layer>` nesting. Do not wrap afy- patterns in
  `<Layer>`; use `cds--layer-*` classes directly if a layered surface is needed.
- Typography always composes Carbon type tokens directly
  (`var(--cds-heading-04-*)`, `var(--cds-label-01-*)`, …); there is no afy
  typography token layer to keep drift surface small.

## 4. Foundation patterns (`foundation.css`)

Prefer the Carbon component first. Reach for a pattern only when the pattern
is app-level and Carbon has no owning component for it.

Global canvas: `.cds--content` paints `var(--afy-canvas)`, so every
workspace backdrop becomes the soft gray (light) / near-black (dark) canvas
without per-page work. The theme root paints the same canvas at viewport
height, so short pages never expose the browser/theme background below the
content. Raised patterns below then read as panels on it.

| Pattern | Use for | Carbon alternative |
|---|---|---|
| `.afy-page__header/__heading/__title/__description/__actions` | Page headers: title at heading-05/600, badge eyebrows, actions right | None (composition) |
| `.afy-page__content` | Single vertical rhythm for stacked sections (grid gap `--afy-space-lg`) | None |

### The expression layer — design decisions (2026 refresh)

The foundation still follows Carbon everywhere it counts: Carbon spacing
rhythm, IBM Plex type scale, support colors, the focus ring, and all
interactive Carbon components. What reads as "2026 modern" lives in how afy-
surfaces express depth, and it is deliberately restrained:

1. **Two-tier surfaces.** The workspace backdrop is the quiet gray canvas;
   content floats on it as raised panels. This is the canvas→card inversion
   that modern clinical products (and Stripe/Linear-class dashboards) share,
   expressed entirely through theme-mapped tokens.
2. **Shell chrome frame.** Carbon renders the sidenav in the same
   background color as the workspace, so in every theme except white the
   rail merges with the canvas. The rail paints `--afy-rail` — one step off
   the canvas per theme (white/g10: white rail on gray; g90/g100: a lighter
   chrome layer, like dark code-editor rails) — plus a hairline edge; the
   header carries the matching hairline to close the frame. Text and link
   colors stay Carbon's.
2. **Carbon product radius only.** afy- surfaces are square like every
   Carbon component (2px corners, 4px on the largest `--afy-radius-lg`
   primitive reserved for future hero surfaces, 100px pills/chips). A
   soft 6/8/12px radius scale was tried on 2026-10-18 and deliberately
   reverted — Carbon components carry no rounding beyond 100px pills, and
   softened surfaces clashed with them.
3. **Hairline + diffuse elevation.** Panels are outlined by a 8–10% ink
   hairline and lifted by a two-stage low-opacity shadow — calm, not
   "drop-shadow heavy". In g90/g100 the shadows switch off and surfaces
   elevate by layer lightness instead (dark themes never fake depth with
   black shadows).
4. **Interaction = shadow + tint + 2px lift** at Carbon's productive tile
   easing (150ms). No bg-color flip alone, no scale transforms. Selection
   reads as a 2px focus-blue inset ring (Carbon's focus token), replacing
   the old gray layer-selected fill.
5. **KPI numerals lead.** Stat values render at heading-04/600 with
   `font-variant-numeric: tabular-nums`, deltas trend in support colors,
   optional icon slot — the dashboard reads as a live clinical board, not a
   form.
6. **Tinted status chips** instead of outline pills: dot + tint + ink all
   derive from the Carbon support colors via color-mix, which keeps exactly
   Carbon's hue but adapts contrast to each theme automatically.
7. **Motion hygiene.** Every foundation transition is disabled under
   `prefers-reduced-motion: reduce`.

Deliberately **not** done (preserving Carbon's character): no glass/blur
shells, no custom fonts, no decorative gradients, no color outside Carbon's
palette, no radius inflation on Carbon components, no forked components.
Pictures of how the expression layer composes: whitish canvas + white cards
with hover lift; dark: g90/g100 canvas with raised layers and focus-blue
selection rings.

## 5. Governance

1. **Placement.** Styling for a shared pattern goes in `foundation.css`;
   styling for one workspace goes in that workspace's legacy file only until
   it migrates; never both.
2. **Override policy for `.cds--*` classes.** Allowed only to fix a documented
   Carbon limitation, in the file owning that UI, with a comment stating the
   limitation and break it fixes. (Existing example: header z-index 8001 in
   `legacy/app-shell.css` — header must paint above the pinned sidenav.)
   Recreating Carbon component behavior with overrides is not allowed; fork
   responsibility stays with Carbon.
3. **`!important`** — forbidden in new code except where Carbon forces it
   (matching its own specificity), with the same documentation rule.
4. **Inline styles in TSX** — allowed only for one-off layout ties between
   state and style. Shared components use classes.
5. **Dark mode.** Every visual change must be verified against g10/g90/g100,
   because tokens auto-flip. A change that looks wrong in dark mode is a bug;
   fix the token usage, never add a dark-mode special case.
6. **Structure freeze (rule 01).** Frontend structure changes require
   updating `rules/01-placement.md`, `eslint.config.js`, and
   `test/structure.test.ts` together (see below — this rule is currently
   breached by `resources/js/shared`, Oct 2026).
7. **CSS size.** foundation.css grows only with patterns reused by 2+
   workspaces. One-off visual polish ships in the workspace's own file or
   inline, then graduates when a second workspace needs it.

## 8. Phases

1. **Phase 1:** structure, tokens, foundation patterns, legacy split.
2. **Phase 2 (this change):** shared components migrated (above); first
   page-level consumers: Admin Index + Platform Overview eyebrows.
3. **Phase 3 — workspaces:** migrate domain by domain (pharmacy, front desk,
 appointments, then the rest), absorbing each legacy file into the
   foundation and deleting it. No domain absorbs more after it starts: each
   migration is one reviewable change.
4. **Phase 4 — fallback cleanup:** each workspace migration replaces literal
   `var(--cds-…, fallback)` pairs with `--afy-space-*` tokens; once all
   workspaces are migrated, trim token fallbacks.
